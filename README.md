# pilot-ipek schedule scraper

Фетчит расписание с `pilot-ipek.ru/raspo/<DD месяц>`, сохраняет в SQLite (сырой HTML +
разобранные занятия) и выдаёт по запросу — офлайн, без повторных походов на сайт.

## Установка

```
bun install
```

## Команды

```
bun run src/cli.ts fetch <дата>              # скачать и разобрать один день
bun run src/cli.ts range <начало> <конец>    # скачать диапазон дат подряд (с паузой между запросами)
bun run src/cli.ts show <дата> [группа]      # прочитать сохранённое расписание
bun run src/cli.ts dates                     # какие даты уже есть в базе
bun run src/cli.ts dump <дата>               # выгрузить сырой HTML на диск для отладки парсера
```

Формат даты: `today` / `tomorrow` / `yesterday` / `DD.MM` / `DD.MM.YYYY`.

Примеры:
```
bun run src/cli.ts fetch 23.09.2026
bun run src/cli.ts range 01.09.2026 30.09.2026
bun run src/cli.ts show 23.09.2026 И-25-1
```

Данные лежат в `./data/schedule.sqlite` (путь можно переопределить через `SCHEDULE_DB_PATH`).

## Архитектура (кратко)

**Задача:** сайт отдаёт расписание только по одной дате за раз и без API — разметка
местами непоследовательная (см. ниже). Нужно фетчить, копить локально и отдавать
без повторных запросов к сайту.

**Решение — три независимых слоя:**

1. **Fetcher** (`fetcher.ts`) — тупой HTTP-клиент с ретраями. Ничего не знает о структуре
   страницы.
2. **Storage** (`db.ts`, SQLite) — хранит **сырой HTML** в `raw_pages` как источник истины,
   и уже поверх него — разобранные данные (`lessons`, `unstructured_blocks`).
3. **Parser** (`parser.ts`) — чистая функция `html -> структура`, ничего не пишет и не
   фетчит. Вызывается отдельно от storage, поэтому её можно прогнать заново по уже
   сохранённому HTML без единого сетевого запроса — важно, раз разметка сайта не
   гарантированно стабильна.

**Ключевое архитектурное решение:** raw-first, а не eager-normalization.

Я не смог посмотреть настоящий сырой HTML страницы (только markdown-выжимку через
доступный мне инструмент, сеть до `pilot-ipek.ru` из моей песочницы тоже недоступна) —
и по этой выжимке видно, что разметка расписания неоднородная: часть блоков — нормальные
`<table>` с `<br>` внутри ячеек (предмет/преподаватель/кабинет построчно), а как минимум
один блок на странице свёрстан иначе, без разделителей между полями вообще.

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Хранить только разобранные данные | Сразу удобный вывод | Один HTML-квирк — и данные тихо теряются/врут, без возможности пересчитать |
| B. Разбирать «на лету» при каждом `show` | Просто | Парсер станет генератором сетевых проблем: любая правка требует пере-фетча |
| **C (выбрано). Сырой HTML — источник истины, разбор — производный, переигрываемый слой** | Ничего не теряется; парсер можно чинить и перегонять данные без единого запроса к сайту; видно, где парсинг не уверен (`confidence: low`, `unstructured_blocks`) | Больше кода, БД немного тяжелее (лежит весь HTML) |

Практическое следствие: `subject/teacher/room` — эвристика с полем `confidence`, а
`raw_lines`/`raw_text` — всегда точная копия текста ячейки/блока. Если эвристика где-то
ошибается — не нужно ничего перекачивать, чинишь `parser.ts` и переразбираешь
сохранённый HTML.

**Что стоит сделать, если будешь дорабатывать под реальный сайт:**
`dump <дата>` сохраняет HTML на диск — открой в браузере devtools, посмотри, как
устроена конкретная ячейка (теги, классы), и подгони `splitCellIntoLines` /
`buildLessonCell` в `parser.ts` под неё. Я специально не гадал вслепую там, где не был
уверен в разметке — такие места помечены как `unstructured` вместо того, чтобы выдавать
правдоподобно выглядящие, но потенциально неверные данные.
